# QQ 终端（行空板 M10）

在行空板的小屏上看 QQ 消息、发快捷回复。

**重活不在板子上。** 维持 QQ 长连接、协议加密那些都由服务器上的
[NapCat](https://github.com/NapNeko/NapCatQQ) 负责，板子只是连过去收发消息：

```
┌──────────────────────┐
│  NapCat / Lagrange   │   跑在服务器上（内存管够）
│  QQ 机器人            │
└──────────┬───────────┘
           │  OneBot 11 协议（WebSocket）
           ▼
┌──────────────────────┐
│  行空板 M10           │   只做两件事：显示 + 输入
│  · 屏幕显示消息        │
│  · 按键/触摸发消息     │
└──────────────────────┘
```

> **为什么不让板子直接跑 QQ？** 试过。桌面版 QQ 是 Electron 应用，
> 起步就要 300~600MB 内存，而板子只有 512MB —— 差一个数量级。
> 详见 `docs/` 里的记录。

## 3. 配置

改 `config.py`：

```python
SERVER_HOST = "1.2.3.4"       # NapCat 所在服务器的地址
SERVER_PORT = 20056                # **外网**端口（NAT 后的，不是容器里的 3001）
ACCESS_TOKEN = "..."               # NapCat 里设的 token
```

> **地址、token、API key 别直接写进 `config.py`。**
> 仓库里这三个字段是空的，真值写在同目录的 `secrets_local.py`（已在
> `.gitignore` 里），`config.py` 末尾会 `from secrets_local import *` 覆盖上来。
> 照 `secrets_local.example.py` 建一份就行 —— 这样 clone 下来也不会把你的
> 服务器地址推上去。没有这个文件程序照样能跑，只是连不上服务器、云端语音不可用。

> 另外 `config.py` 里有个 `DEMO_MODE = True`：**不连服务器、不登 QQ**，
> 直接喂 `democlient.py` 里的假消息。调界面和输入法时用这个，
> 免得一个 QQ 号登两处互相挤下线。接真号改成 `False`。

### NapCat 那边要做的

1. 装好 NapCat 并登录 QQ（扫码）
2. 打开 NapCat 的 WebUI（默认 6099 端口）
3. **网络配置 → 新建 → WebSocket 服务器**
   - Host: `0.0.0.0`
   - Port: `3001`
   - Token: 随便设一个，填进板子的 `config.py`
4. 记下端口，和服务器地址一起填进 `config.py`

> **服务器是 NAT 的话**，还要在母鸡面板里把 `3001` 转发到小鸡的 `3001`，
> 板子才连得上。

## 5. 为什么用 OneBot 协议

OneBot 11 是 QQ 机器人框架的**通用协议** —— NapCat、Lagrange、go-cqhttp 都实现它。

好处：**换框架时板子这边一行都不用改**，只改 `config.py` 里的地址和端口。

## 7. 排错

| 现象 | 原因 / 处理 |
|---|---|
| 圆点一直是红的 | 连不上 NapCat。检查 `config.py` 的地址端口、NapCat 的 WebSocket 服务是否开着 |
| 圆点黄的，一直转 | 连接中。服务器在国外的话延迟可能几百毫秒 |
| 提示"没装 websocket-client" | `pip3 install websocket-client` |
| 收得到消息但发不出去 | NapCat 的 token 填错，或 token 权限不足 |
| 发出去但对方没收到 | 看聊天页有没有出现绿色消息；有就是发出去了，对方没收到是 QQ 那边的事 |
| 消息显示 `[图片]` `[表情]` | 正常 —— 240×320 的屏显示不了图片，用占位符代替 |
| `@…` 一直没有变成名字 | 那个人退群了 / 号注销了，查不到。只查一次，不会一直重试 |
| 界面盖住了 Home 菜单 | 点右上角 ✕，或按板子的 Home 键 |
| **消息多了以后卡** | 曾经真的卡：折行是逐字符问 Tk 字宽（单次 4.19ms），300 条消息要 **67 秒**。现在字宽和每条消息的折行结果都缓存了，同样的 300 条 **0.32 秒** |
| 按住 A/B 松手后界面还在动 | 曾经的事件队列每轮只取 1 个（`sleep(0.2)`），键重复会积压。现在主循环 `drain()` 一次取完 |

## 8. @ 怎么显示成名字的

QQ 的 at 段里**只有 QQ 号，没有名字**：

```json
{"type": "at", "data": {"qq": "3890902844"}}
```

直接显示就是 `@3890902844` —— 小屏上一串数字又长又没用。所以名字分两个来源补：

1. **成员表**（主要来源）：每收到一条群消息，就把发送者的群名片记进
   `(群号, QQ号) → 群名片`。群里说话的人基本就是会被 @ 到的人，攒一会儿
   大多都有了，不用打电话问服务器。
2. **现查**：表里没有的走 `get_group_member_info` 单查（**不是**
   `get_group_member_list` —— 后者一次几百人的 JSON，512MB 的板子不划算）。
   实测 0.2 秒/人，后台串行查，不卡界面。

难点是**名字是异步到的**，而消息早就画到屏幕上了。所以正文里先埋一个
占位符 `⟨at:0⟩`（序号，**不是 QQ 号**），名字到了再回填，详见下面"为什么
占位符里不放 QQ 号"。

时序：

```
消息到  →  埋占位符  →  立刻显示 "@…"     ← 用户先看到是谁在说话，不是一片空白
                ↓ 后台查
           名字回来  →  回填  →  屏幕上的 "@…" 变成 "@清风明月"
```

**距离：全程不显示 QQ 号。** 查不到就显示 `@…`，宁可不知道是谁，
也不把号码摊在屏幕上。

### 为什么占位符里不放 QQ 号

放号码的话，万一哪天有个显示路径漏了 `resolve_at`，屏幕上就是一串数字；
放序号的话，最坏也不过是显示出 `⟨at:0⟩` 这种一看就知道是内部标记的东西。

同理，占位符要**带序号**：一条消息 `@张三 @李四`，两个都用 `"@…"` 当
占位符的话，回填时第一个会把第二个覆盖掉，分不清谁是谁。

### 群号必须参与查询

成员表是 `(群号, QQ号)` 两级的。不同群里同一个 QQ 号是**两个人**，
拿全局表按 QQ 号直接查会张冠李戴。

## 9. 打字输入和语音

### 两种输入走同一个缓冲区

核心约束是"**语音识别出来的文字要能再用键盘改**"。这一点决定了整个输入层的架构：

```
        ┌─────────────┐
键盘 ──▶│             │
        │  TextBuffer │──▶ 发送
语音 ──▶│             │
        └─────────────┘
```

语音**不直接发出去**，识别结果走 `TextBuffer.insert()` 落进输入框 ——
和键盘敲进去的是同一条路径，所以之后退格、左右移动、撤销全都好使。
`test_input.py` 里专门有一组用例盯着这件事。

### 不用等消息就能看到群和好友

连上后拉 `get_group_list` + `get_friend_list`，**直接把这些会话建出来**
（空的，只有名字）。所以想主动给谁发消息，不用等对方先开口。

列表顺序：

```
有消息的会话      按最后一条消息的时间排，最新的在最上面
─────────────────────────────────────
空会话（纯名单）  垫底，顺序固定不跳（跳了手指会点错）
```

空会话的预览行会显示「群里还没人说话」/「还没聊过 · 点进去发消息」，
点进去就能发。

⚠️ 会话 id **必须统一成 int**。消息事件里 `group_id` 是 JSON 数字，
而缓存里是字符串 —— 不统一的话同一个群会建出两个会话（一个带消息、
一个空）。见 `Store.norm_sid()`。

`config.MAX_SESSIONS` 要 ≥ 群数 + 好友数，否则装不下。

### 操作

聊天页点中间 → 菜单第一项「打字发送」。

```
┌────────────────────┐
│ 发送消息          ✕ │  标题栏兼提示行
├────────────────────┤
│ 你好世界|          │  4 行，光标按像素定位
│                    │
│                    │
│                    │
├────────────────────┤
│ 你 尼 泥 拟         │  候选栏（只有中文组字时出现）
├────────────────────┤
│ q w e r t y u i o p│  ← 每键 24×37px
│  a s d f g h j k l │     约 4.3×6.6mm
│  ⇧ z x c v b n m ⌫ │
│ 123 中/英 语音 空格 发送│
└────────────────────┘
```

**键盘有三页，左下角那个键切换：**

| 页 | 入口键 | 内容 |
|---|---|---|
| 字母 | — | qwertyuiop / asdfghjkl / ⇧ zxcvbnm ⌫ |
| 数字 | `123` | 1~0，加上 `，。？！、：；（）` 和 `. , ? ! ' " /` |
| 符号 | `#+=` | `@#$%&*-+=/` `¥~^\|!?:;` `.,"'()[]` |

- 三页**键位几何完全一样**（每行 10/9/9/5 个键），切页只换键帽上的字。
  这是硬要求：键盘控件只在启动时建一次，位置还被输入界面的显隐逻辑
  记着，重排坐标会让整套控件错位。
- 数字页第 2 行故意放**中文标点** —— 打中文时 `，。？！` 最高频，
  不用切输入法就能直接按
- **左下角那个键**轮流切四态：`中文 → 英文 → 中文字符 → 英文字符 → 中文`。
  键上显示的是**当前状态**（中/英/中符/英符），不是"按了会跳到哪"。
  两个字符页都带一整行数字 `1234567890`，中文页是 `，。？！`，英文页是 `@#$&*-+=/`。
- **⇧** 大写（按一次管一个字母）
- **语音**：点一下开录，**再点一下停**。不做静音检测 —— 什么时候说完
  交给云端判断（本地那套阈值调不准：底噪 255~300，稍不留神就把
  噪声当人声、或者用户刚按下还没开口就收尾了）。30 秒自动兜底。
- **A / B 键**：输入界面里当左右移光标用（板子没有方向键，
  手指又点不准字缝）
- 点文本区任意位置可以把光标挪过去

### 拼音候选从哪来

`pinyin_ime.py` 建索引时读两份**预生成**的数据文件：

| 文件 | 内容 | 生成方式 |
|---|---|---|
| `ime_words.txt` | 6000 个高频词 + 拼音（行序 = 词频） | `python3 gen_words.py` |
| `ime_chars.txt` | 11580 个单字频次 | 同上 |

为什么要预生成：现算的话要解析 jieba 的 34 万行词典 + 6000 次
`lazy_pinyin`，在 RK3308 上 **39 秒**；读文件只要 14 秒里的一大半
是不读它也要做的建表工作。改了词典就重跑一次 `gen_words.py`。

**边打边猜**：打到一半（`ces`）音节切不开，会拿整串去词库做前缀匹配
（`ceshi` → 测试）；两个字母以内（`zh`）改给按字频排好的单字
（这/中/着…），不会冒出一串字母序的冷僻词。

### ⚠️ 每键只有 4.3mm

2.8" 屏，1px ≈ 0.178mm。竖屏放 10 列，每键 24px = **4.3mm**，
只有成人指尖（约 9mm）的一半 —— 会误触，这是**硬约束不是没调好**。
所以配了大号退格（36px）、光标键、撤销来兜底。

### 拼音词库从哪来

**板子上已经装好的 `pypinyin`**，零新增依赖：

| 数据 | 条数 | 用途 |
|---|---|---|
| `pinyin_dict` | 41497 字 | 拼音 → 候选字（反着用它） |
| `phrases_dict` | 45471 词 | 整词候选（`nihao` → 你好） |

⚠️ pypinyin 本身是**汉字→拼音**方向的，这里把它倒过来用。
两个必须处理的点：

- **去声调**：用户敲 `ni` 不是 `nǐ`。但 `ü` 是特例 —— 直接滤声调符号
  会变成 `u`，而输入法里 ü 是打 `v` 的（女 = `nv`）。
- **音节切分**：`nihao` 要切成 `ni`+`hao`。音节表不另外找，
  直接从 `pinyin_dict` 的值里收集（那本来就是全部合法音节）。

索引**懒加载**（第一次进输入界面才在后台建）—— 解析 8 万条在
RK3308 上不是一瞬间的事，不能拖慢启动。

候选排序用文件里附的常用字表，否则 `ni` 第一个候选是「尼」不是「你」。

### 语音：云端 Deepgram 主力 + 本地 Vosk 兜底

```
按键开录 ──▶ 只采集，不解码（云端模式下把 CPU 全留给录音，一帧不丢）
              │
          再按一下停（不做静音检测，交给云端；30 秒兜底）
              ├──▶ 云端 Deepgram（后台线程，整段 WAV 原样发，不裁剪）
              │      成功 → 用云端文本
              │      失败/超时 → 用本地 Vosk 的结果，并在标题上说明
              └──▶ 文本走 TextBuffer.insert，和键盘同一条路径（可改）
```

为什么云端当主力：本地 Vosk small-cn 词错率约 **23.5%**（四五个字错一个），
实测没法用。Deepgram nova-3 中文好一个量级。

配置（`config.py`）：

```python
ASR_PROVIDER = "deepgram"      # "none" = 只用本地、不上传音频
DEEPGRAM_KEY = "..."           # 填在 secrets_local.py 里
DEEPGRAM_MODEL = "nova-3"
DEEPGRAM_LANG = "zh-CN"        # 说英文多就改 en-US
CLOUD_TIMEOUT = 30.0           # 见下面「慢」那条
MAX_REC_SEC = 30.0             # 单次录音上限
```

**为什么超时给到 30 秒**：板子上传带宽有限，实测 3 秒音频 2.4 秒往返、
10 秒音频 8.5 秒往返（大约每 1 秒音频 0.8 秒）。30 秒上限最坏要 25 秒左右，
给 30 留点余量。等待期间标题栏会显示「云端识别中… N 秒」，不会让人以为卡死。

本地 Vosk 还是要装（兜底用）：

```bash
pip3 install vosk            # ≈20MB
mkdir -p /root/M10_QQ/models && cd /root/M10_QQ/models
# 从 https://alphacephei.com/vosk/models 下这两个：
#   vosk-model-small-cn-0.22      中文  42MB  词错率约 23.5%
#   vosk-model-small-en-us-0.15   英文  40MB  词错率约 9.9%
```

**中文词错率 23.5% 意味着每四五个字错一个。** 这是设计前提不是缺陷 ——
语音负责出草稿，键盘负责改。

没装 Vosk / 模型没下 / 路径写错 → 语音键自动变灰，**键盘和收发消息
完全不受影响**（`voice.py` 的工厂函数一律退回 NullEngine）。

### 还没确认清楚的几件事

| 要验的 | 怎么验 |
|---|---|
| **Vosk 速度**（最大风险） | RK3308 是弱 CPU，说 5 秒的话可能要转好几秒。太慢就改用板子上已装的讯飞（`df-xfyun-speech`，零安装） |
| **内存** | 512MB 里塞 40MB 模型够不够（app 本身已占约 58MB） |
| **录音声道数** | 记录里写着"必须双声道"，但 DFRobot 官方 `unihiker/Audio.py` 写死单声道 —— **两者矛盾**。代码会自动两种都试并打日志 |
| **`state="hidden"` 是否生效** | unihiker 的矩形自己按 fill 设 state，可能会覆盖。代码里加了"挪到屏幕外"的兜底 |
| **界面观感** | 键盘布局、候选栏、光标位置 |
